# Public release checks

Both Pages publication workflows use the repository-wide `pages` concurrency group with `queue: max` and no cancellation. They test the checked-out files before staging, archive only the committed revision, reject a changed main immediately before deployment, and check the deployed revision and critical asset hashes afterwards. A failed check makes that workflow fail; a post-deployment failure needs investigation and, if necessary, a revert. It does not automatically roll production back.

The gate uses Node 24, Python 3.12 with lxml 6.1.3, and Playwright 1.56.1 with Chromium and WebKit. Run `node scripts/verify_public_release.cjs` after installing those dependencies. `PYTHON`, `NODE_PATH`, `PLAYWRIGHT_BROWSERS_PATH` and `RELEASE_BROWSER_EXECUTABLE` can point to local test tools. `--browser-only` repeats just browser checks. The default covers both engines; `RELEASE_BROWSERS=chromium` is a partial run and must be reported as such.

The browser suite starts a temporary loopback server, blocks external HTTP and WebSockets, and uses explicitly synthetic stock data. It covers four widths (1440, 768, 390 and 375), navigation, search/empty states, website quantitative snapshot loading, stale status, research and persistence, source-stop races, storage failures, and calendar transitions. Reports and screenshots go into `audit/browser-output/release/`, which is ignored by Git. These are offline product checks, not confirmation of external quote accuracy, private authentication, production D1 writes, or the Mac research daemon. The gate also runs the public quantitative collector and engine's injected offline tests.

`scripts/stage_public_release.cjs` requires `EXPECTED_SHA` and a new absolute `BOOKS_STAGE_DIR` outside the checkout. It rejects dirty tracked files and builds from `git archive`, so untracked working files cannot accidentally be published and all committed position history remains present. Private service/configuration, paper administration, test fixtures and workflow files are excluded. The artifact includes `release-manifest.json` with the exact revision and public code asset hashes.

After publishing, `EXPECTED_SHA=<deployed commit> RELEASE_BASE_URL=https://sking-3.github.io/xuanliu-site/ node scripts/verify_public_release.cjs --live` checks the manifest, 21 critical asset hashes, and both isolated browser suites against the hosted files. It never follows a redirect or retries 401/403/429. A matching manifest and passing mocked interactions do not attest every live data source.

PRs targeting main and the integration branch run the same offline checks. Live checks are part of each deployment job and do not depend on a commit-message label. UI-only releases should retain the existing `[ui-only]` marker so the separate collection workflow respects its existing no-source-access behavior. Do not change paused jobs, source-stop records or refresh scopes to make a UI release pass.

For a UI-only push, the refresh workflow checks out `github.event.after` rather than a moving main. The existing resolver then requires exact event/checkout SHA equality before emitting `skip`; all source collection steps remain gated on that result. Scheduled, manual and non-UI refreshes still check out the latest main so they retain current source-stop records. A squash merge must explicitly supply a commit title containing `[ui-only]`; rebasing without controlling the final commit message is unsuitable. If main advances, the later snapshot/publication guard rejects the obsolete artifact without source access.

The independently triggered homepage workflow is also offline for both main pushes and manual dispatches. It no longer invokes `home-provider-browser.cjs`; that retired entry point exits with an explicit failure before any browser or network dependency loads. Its replacement, `home-dashboard-browser.cjs`, requires an explicit loopback server, blocks service workers and unknown WebSockets, mocks the known provider responses, and follows no redirects in local link checks. A main push changing `index.html` must not silently turn this check into live quote collection. See [the homepage CI source audit](HOMEPAGE-CI.md).

Rollback uses a reviewed revert of the relevant integration commits on the latest main; do not reset or force-push over later history. The revert must pass the same gate and its actual deployed revision must be checked. Private migrations and the local research service have separate release/rollback plans and are outside this public release.
