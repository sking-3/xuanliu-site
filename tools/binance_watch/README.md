# Binance 公开操作记录监控

## 当前实现

`public_orders.py` 独立读取熬鹰资本的公开操作记录。官方未登录页面的“最新操作记录”及原站 `lead-portfolio/order-history` 均公开可读；这与隐藏的当前仓位是两种权限。当前仓位仍不请求，原有拒绝记录不清空。

- 目标每 5 秒发起一次请求，分页同样保持至少 5 秒间隔；不重叠、不补发积压节拍。
- 实际接口没有订单 ID。按规范化公开记录生成指纹去重，分别记录首次出现、可能修订和间隙后发现。创建时间等字段相同不能证明是同一订单；不同完整指纹不合并，分别保留首次发现时间。方向只表述开仓或加仓方向，不能证明新建仓位。
- 首次历史全部建立基线。来源创建时间、更新时间、实际读取时间和首次发现时间分开保存。
- 发现观察间隙后补查有界七日窗口，正常连续观察每五分钟补查一次，补查仍遵守分页上限和五秒间距；后页延迟记录按迟到记录保存。达到十页上限仍标注覆盖不完整，不承诺完整历史。
- 已核实每页最多 20 条，使用 `indexValue` 翻页；边界会重复一条，需要去重。首次两页合计 38 条唯一记录。
- 2026-11-11 的本地有界实测完成 13 次真实请求，请求启动间隔 5.002～5.009 秒，均返回成功。它不代表币安公开承诺的配额或来源刷新延迟。
- GitHub 工作流为 `binance-public-orders.yml`。检查点保存在独立的 `binance-public-orders-state` 分支，通过文件 SHA 比较后更新；首次来源请求前先保存运行占用标记。403/429、状态冲突或未完整结束的上次运行均停止，不重建检查点绕过。
- 来源任务使用专用交易所并发锁，已禁用的旧 Python 仓位观察器保留同一把锁。旧全站任务的 Node 币安云端入口已硬停止，因此其非币安工作不再阻塞此来源；已有来源停止记录不变。旧排队观察任务因缺少 public-records-v3 运行栅栏，在读取状态或来源前停止。检查点 SHA 占用与每轮核验继续防止迁移期间双重请求。检查点只访问 GitHub 仓库内容 API，不查询受限运行队列。
- 不请求隐藏仓位、未成交挂单，不交易、不登录币安、不读取用户密钥、不发送外部消息。

GitHub 云端已完成一次真实来源实测：[运行 43011772192](https://github.com/sking-3/xuanliu-site/actions/runs/43011772192)。61.524 秒内完成 13 次成功请求，启动间隔 5.001～5.080 秒，建立 38 条历史基线，未把旧记录当新信号，检查点已正常封存。实测期间没有新增公开记录，不能据此断言账户没有交易。

自动运行采用单链接续，不依赖 GitHub cron。初次 main 上观察器变更触发 65 秒实测；此后每轮最多观察 14 分钟，正常封存检查点后，只发起一次同一工作流的 workflow_dispatch。每个接续标记先经文件 SHA 比较后保存，再提交触发；下一轮必须消费准确标记，代码发布不能建立第二条链。访问拒绝或触发结果不明时停止，不重试、不重置停止记录。运行标记升级为 public-records-v3，旧排队定义不能读取来源。GitHub 启动仍可能留下间隙，不能称为全天无缝实时。没有站外消息推送。

触发只用该来源 job 的临时 GITHUB_TOKEN，增加该 job 的 actions:write 权限；没有新增长期令牌或私钥，不读取运行列表或队列。GitHub [官方文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)明确允许 GITHUB_TOKEN 触发 workflow_dispatch。触发 HTTP 204 只表示已接收，必须另验下一轮的 parentRunId、workflow_dispatch 触发类型及实际来源成功时间，才能确认自动接续。

熬鹰的现有详情页从独立检查点读取真实公开记录，打开详情后每分钟检查保存结果。来源时间、首次发现时间、数量及计价单位分开展示；界面不直接请求币安，保存时间过期时明确提示。来源无订单 ID，列表不合并仅时间和方向相同的不同来源记录，不据此推算胜率或收益率。

## GitHub 运行配置（待启用）

工作流：[`binance-python-watch.yml`](../../.github/workflows/binance-python-watch.yml)。

- 待启用方案的定时点为每小时第 3、18、33、48 分钟；每次运行最多 840 秒（14 分钟）。当前 cron 只保留为注释。
- 正常运行期间以 **5 秒为目标检查节拍**，不重叠请求、不补发错过的节拍。响应较慢时会跳过节拍。
- 每轮先核验准确组合 ID、ACTIVE 状态和 `positionShow=true`，再读取仓位和公开历史订单第一页。来源请求至少相隔 2 秒。
- 本目录或工作流的代码进入 main 后，push 验证运行 60 秒。手动触发可选择有界运行时间。
- 与既有币安采集共用来源任务并发锁，并双向核验停止记录；不会同时请求来源。不循环提交 Git 快照。
- 每次结束将 SQLite 检查点保存为 `binance-watch-state` Actions artifact，下一次读取同工作流之前运行的有效检查点。保留期 30 天。

**GitHub 托管执行不能保证全天连续每 5 秒。** 即使定时任务准时，也有约 1 分钟的计划间隙，另有排队、环境启动和状态交接耗时。GitHub 定时任务还可能延迟。旧网站全量刷新会持有来源锁约几十分钟，此时本监控等待；旧刷新任务等待监控时，也可能间接推迟网站的数据发布。纯界面修改不占来源锁。定时监控只使用本轮创建后 840 秒内的剩余预算，过期本轮跳过，不能把排队积压变成连续补采。没有运行的时间就是观察盲区，不能补成连续监控。来源本身何时更新也没有秒级保证。

每 5 秒三次请求相当于连续运行时每天约 51,840 次来源请求；实际次数受运行间隙影响。本工具没有把该数值当作币安公布的配额。遇到限流或访问拒绝即持久停止，不换 IP、端点、身份或客户端重试。

## 数据及状态

只使用新版 Copy Trading 的 `portfolioId`。不将数字组合 ID 错当作旧排行榜的 `encryptedUid`。

- 首次有效快照仅建立基线，不把已有仓位报为新开仓。
- 比较规范化十进制数量；`1` 与 `1.0` 不产生伪变化。
- 记录仓位出现、数量增加或减少；仓位连续两次缺失才确认从快照消失。
- 空仓也是有效快照，因此空仓之后首次出现的仓位可以被观察到。
- 重启、观察中断或请求失败后重新建立基线，不能断言盲区内发生了什么。
- `observedAt` 是本工具实际读取时间。来源未给更新时间时保持空值，不能用读取时间冒充成交时间。
- 这些是**仓位快照变化**，不是逐笔成交或完整交割单。无法捕捉两个快照之间已经开平的仓位，也不能从仓位差值判断具体成交价格、手续费或精确开仓时间。
- 保留最新快照和最多 10,000 条观察事件，不无限保存每 5 秒的完整仓位。

HTTP 401/403/418/429、挑战响应、来源业务错误、隐藏仓位、身份不符或结构变化均停止本监控；下一次任务读取停止状态后不会继续来源请求。仓库现有 `trader/binance/portfolios.json` 和旧版 `snapshot.json` 的停止状态同样检查。

HTTP 202/401/403/418/429/451 和来源业务拒绝沿用仓库原有全局停止口径，旧采集器也会停止请求。仅目标组合的明确隐私/非活跃状态不会自动关闭另外三个公开组合；未知或不完整的交接记录仍停止对应采集并要求检查。

上次运行异常中断、状态缺失、损坏、已过期或无法证明此前未运行时，停止并在 Actions 日志说明原因。只有可确认的首次运行可以初始化空状态。不要通过删除 artifact、重置数据库或重复运行来清除拒绝记录。

## 验收

在仓库 Actions 中打开 **Bounded Binance Python watch**。当前应看到离线测试通过、Monitor public positions 被跳过。后续启用后，分别检查触发类型、实际开始和结束时间、轮次日志、停止原因以及 artifact。`push` 或 `workflow_dispatch` 成功不等于 `schedule` 已验收；必须有实际 `event=schedule` 记录。

## 官方运行限制

[GitHub 的 schedule 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)说明定时最小间隔为 5 分钟，并可能出现延迟。本方案的 5 秒节拍发生在已启动的 Python 进程内，不是 5 秒 cron。

## 指定组合的订单观察

本地及 GitHub 审查分支使用相同组合 ID。已有记录为 `positionShow=false`，此后的公开仓位、订单可见性、此接口用途与请求额度均未核实。目标停止项与来源级停止项在初始化 Transport 和 SQLite 前检查。真实工作流继续关闭。

可读性和频率以后都得到核实才可能使用的实现，每轮先读组合可见性，再读仓位和公开历史订单首页（最多 20 条）。三个来源请求间至少 2 秒。即使设为每 5 秒一轮，响应或排队也可能造成空档；连续运行的理论上限约 51,840 个请求/天。GitHub 的 cron 无法提供每 5 秒触发。

只有稳定订单 ID、连续观察，且来源创建时间晚于上一次成功读取，才记为新订单。已有订单累计成交量增加单独记录，不能据此确认逐笔成交或一次新开仓。无 ID 的行只计数，首次读取、盲区后读取只建基线；同一事务保存仓位、订单页及事件。报告使用来源创建/更新时间、首次发现时间和本次观察时间。仓位比较独立于订单比较。不完整分页或观测空档均不能证明没有订单。未接入推送通知。

离线验证（Python 3.11 及以上）：`python3 -B -m unittest discover -s tools/binance_watch -p 'test_*.py'`。GitHub 的专用审查分支只允许离线测试，无定时采集。
